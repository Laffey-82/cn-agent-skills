# 常见根因模式

## 先按概率排序

排障先查高频原因,再查低频:

1. 数据问题(输入、状态、脏数据);
2. 环境问题(版本、配置、时区);
3. 逻辑问题(边界、并发、顺序);
4. 依赖问题(第三方行为、网络);
5. 资源问题(内存、连接数、磁盘)。

## 高频根因清单

| 模式 | 症状 | 确认方法 |
|---|---|---|
| 浮点精度 | 金额/比例算错 | 日志打中间值,改用整数或 Decimal |
| 时区错乱 | 时间差 8 小时/1 天 | 查存储与展示的时区是否一致 |
| 缓存未失效 | 改了不生效、数据旧 | 查缓存 key 和失效逻辑 |
| 并发竞态 | 偶发、压测才出现 | 加日志看请求顺序,查锁和原子性 |
| N+1 查询 | 慢,数据量一涨就崩 | 慢日志/EXPLAIN |
| 索引失效 | 慢查询 | EXPLAIN 看是否全表扫描 |
| 空指针/缺字段 | 偶发崩溃 | 查上游返回结构变化 |
| 编码问题 | 中文乱码 | 查字符集和传输编码 |
| 内存泄漏 | 随时间变慢/崩 | 内存监控,heap dump |
| 连接池耗尽 | 高峰期报连接超时 | 查连接释放是否遗漏 |

## 二分定位法

在"输入 → 处理 → 输出"链路上:

1. 从中间点验证,确认问题在前半段还是后半段;
2. 缩小区间,继续二分;
3. 每次改动只动一个变量。

git 场景用 `git bisect` 定位引入问题的提交。

## 报告模板

```markdown
# Bug 排查报告

## 现象
## 复现步骤
## 根因
## 修复
## 回归验证
## 预防
```

## 预防思路

- 修复后问"还有没有类似的地方",批量处理;
- 把这次的经验写进代码注释或团队文档;
- 能加测试的就加回归测试,一次修复一次沉淀。
