# 缓存三类故障与防御

## 穿透

**场景:** 查不存在的 key,每次都打到数据库。

**防御:**

- 参数校验,非法参数直接拒绝;
- 空值也缓存(短 TTL);
- 数据量大的场景用布隆过滤器。

## 击穿

**场景:** 热点 key 过期瞬间,大量请求同时回源。

**防御:**

- 互斥锁:只允许一个请求重建缓存,其余等待;
- 逻辑过期:值里带过期时间,过期后异步刷新;
- 热点 key 永不过期,靠后台任务更新。

## 雪崩

**场景:** 大量 key 同一时间过期,数据库被压垮。

**防御:**

- TTL 随机化(偏移不超过基础值 10%);
- 多级缓存(本地缓存 + 分布式缓存);
- 限流降级,数据库扛不住时直接返回降级结果。

## key 与 TTL 设计

### key 规范

```text
业务:对象:版本:标识
user:info:v1:12345
order:detail:v1:67890
```

要求:带业务前缀、带版本号、标识放最后。

### TTL 原则

- 每个 key 有 TTL,或明确"为什么不过期";
- TTL 和业务可接受的一致性窗口匹配;
- 更新频繁的数据 TTL 短,稳定数据 TTL 长。

## 一致性

- 更新数据库后删缓存,下次读取重建(推荐);
- 先删缓存再更新数据库,会有短暂窗口读到旧值;
- 一致性要求严格的场景,TTL 要短或不用缓存;
- 缓存服务不可用时,业务直接查库(降级)。

## 常见排查问题

1. 命中率为什么低?→ 检查 key 是否带业务前缀、TTL 是否太短;
2. 为什么数据是旧的?→ 检查失效逻辑和 TTL;
3. 为什么数据库压力大?→ 看回源率,排查穿透/击穿/雪崩。
