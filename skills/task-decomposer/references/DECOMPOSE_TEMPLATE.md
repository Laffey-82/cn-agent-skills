# 任务拆解模板

## 任务清单模板

```markdown
# 任务清单:<目标>

| # | 任务 | 依赖 | 交付物 | 验收标准 | 预估 |
|---|------|------|--------|----------|------|
| 1 |  |  |  |  |  |

## 推荐提交顺序

## 风险与不确定项
```

## 判断拆得好不好

一个任务满足这五条,才算拆好:

1. 单一职责:只做一件事;
2. 可独立完成:不依赖未完成的任务;
3. 可验收:有明确的完成标准;
4. 可估算:能估计工作量;
5. 可提交:完成后能形成一次有意义的 commit。

拆完逐条核对,不满足就继续拆或合并。

## 依赖排法

- 有先后关系的排顺序:A → B → C;
- 互不影响的标"可并行";
- 不确定的标"需调研",先做调研任务;
- 依赖别人的任务拆出"等待"状态,不等别人也能推进的部分先做。

## 常见拆法

| 场景 | 拆法 |
|---|---|
| 新功能 | 数据层 → 接口 → 前端 → 联调 → 部署 |
| 重构 | 摸底 → 写测试 → 分模块重构 → 全量回归 |
| Bug 修复 | 复现 → 定位根因 → 修复+回归测试 → 验证 |
| 调研 | 问题定义 → 资料收集 → 方案对比 → 结论输出 |

## 验收标准怎么写

能观察、能验证,不要"做好""优化一下":

| 差 | 好 |
|---|---|
| 实现登录 | 正确账号密码返回 token,错密码返回 401 |
| 优化性能 | 列表接口从 2s 降到 500ms 以内 |
| 写文档 | README 含快速开始,照做能跑起来 |
