# 技能风格审查判断标准

配合 [scripts/style_checker.py](../scripts/style_checker.py) 使用。脚本负责把可疑点标出来,这份文档给出每条标记的判断标准和改法。脚本的结论只算线索,最终判断以这里和 [docs/STYLE_GUIDE.md](../../docs/STYLE_GUIDE.md) 为准。

## 检查流程

1. 跑脚本,把机器能标记的项过一遍:

   ```bash
   # 检查全部技能
   python skills/skill-style-guide/scripts/style_checker.py

   # 只检查一个技能
   python skills/skill-style-guide/scripts/style_checker.py api-tester
   ```

2. 对照下面的判断标准,逐条确认标记是否成立;
3. 能当场改的直接改,改完重跑脚本;
4. 脚本覆盖不到的项目,按文末的"人工检查项"过一遍;
5. 输出审查结论(通过 / 修改后通过 / 不通过)。

## 标记项判断标准

| 脚本标记 | 级别 | 判断标准 | 处理建议 |
|---|---|---|---|
| 目录名不合规 | 必须 | 名字应小写、连字符、以字母开头,一眼能看出"做什么" | 用动词短语重命名,并同步改 name |
| frontmatter 缺 name | 必须 | 没有 name 技能无法被 Agent 识别 | 补上,与目录名一致 |
| name 与目录名不一致 | 必须 | 两边不一致会导致安装后找不到技能 | 统一成同一个名字 |
| frontmatter 缺 description | 必须 | 没有 description 就不知道什么时候触发 | 写清"做什么 + 何时触发" |
| description 疑似空泛 | 建议 | 判断是否只说"帮助用户做 XX",没说清场景和产出 | 改成具体场景,例如"当需求模糊、缺少验收标准时" |
| description 无中文 / 无英文关键词 | 建议 | 仓库面向中文用户,描述要覆盖中文说法,英文关键词方便检索 | 中文为主,附上英文关键词 |
| 缺 license | 建议 | 开源仓库建议写明授权 | 补 `license: MIT` |
| 缺 metadata.version | 建议 | 技能有版本号,后续迭代能对上 | 补 `metadata: version` |
| SKILL.md 超 500 行 | 必须 | 正文过长,Agent 一次读不完 | 把细节、模板、长例子拆到 references/ |
| 缺"验证方式" | 必须 | 没有验证方式,装完不知道有没有生效 | 写清触发词、执行位置、预期产出 |
| 缺"不适用场景" | 建议 | 不写清楚,容易在无关任务上误触发 | 列出明确不该用本技能的情况 |
| 代码围栏数量为奇数 | 必须 | Markdown 会渲染错乱,示例没法看 | 数一遍 ``` 配对,补全或删掉多余的 |
| 疑似空泛表述 | 建议 | 看上下文,如果是"认真分析"这类指令就成立 | 改成具体动作:查什么、怎么查、产出什么 |
| 标题或连续 emoji | 建议 | 文案标准是自然表达,不靠 emoji 撑场面 | 删掉标题里的 emoji,正文里不超过一个 |

## 人工检查项

脚本覆盖不到,但合并前必须人工确认:

- 步骤是否具体到 Agent 照着就能做,不依赖"进一步分析"这类含糊指令;
- 规则是否都配了示例,示例是否可运行(脚本示例要实测过);
- description 是否覆盖真实的中文触发说法;
- 内容是否原创,不搬运、不改写来源不明的资料;
- 是否写清了输入和产出,让用户知道装完能拿到什么;
- 辅助脚本是否只做标记或测量,结论由人确认。

## 常见误判

脚本标记不等于必须改,以下情况通常可以保留:

- 引用示例里的空话和 emoji(比如在教"什么是空泛表达"时举例);
- 表格里用于对比的写法;
- 术语、命令、代码里的关键词,不属于文案范围。

拿不准的时候,先问一句:这句话删掉,技能会不会变差?不会,就删;会,就保留。
