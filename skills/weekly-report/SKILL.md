# 周报生成

## 何时使用

- 用户说"帮我写周报""这周做了啥";
- 周五下班前或汇报前,需要整理本周工作;
- 有 git 历史可用,想快速把提交变成周报素材。

## 使用步骤

### 第 1 步:确认时间段与范围

- 默认本周一至今;也可按汇报要求指定起止日期;
- 涉及多个仓库时,一次列出全部路径;
- 确认周报给谁看(自己、组长、客户),语气和颗粒度不同。

### 第 2 步:收集事实

跑脚本收集提交素材,命令见下面的[辅助脚本](#辅助脚本)。脚本只收集和分组事实:提交、作者、类型、文件数;琐碎提交(merge/typo/格式化)单独列出,不混进正文。

### 第 3 步:补充提交之外的工作

git 提交覆盖不到的,问用户或从对话里找:

- 开会、评审、沟通、协调;
- 进行中的事项和进度;
- 风险、阻塞、需要别人配合的;
- 下周计划。

### 第 4 步:写成周报

按下面的结构组织,事实以脚本输出为准,不编造:

```markdown
# 周报:2026-08-24 ~ 2026-08-30

## 本周完成
- 按类型或项目分组,每条一句"做了什么",可带提交号
## 进行中
- 事项 + 当前进度
## 风险与阻塞
- 有问题直说,给出需要的支持
## 下一步计划
- 可执行、有优先级
```

原则:

- 结论比数量重要:写"上线了 X 功能",而不是"提交了 20 次";
- 提交号放括号里作证据,不占正文;
- 琐碎提交不写进正文。

### 第 5 步:确认后交付

- 让用户过目,确认没有夸大、没有漏掉关键工作;
- 要存档或发群,按用户要求输出文件或直接给文本。

## 输入与输出

- 输入:git 仓库路径(可选多个)+ 时间范围 + 用户补充的工作事项;
- 输出:结构化中文周报。

## 示例

**用户输入:** "帮我写这周周报。"

**脚本输出(节选):**

```text
- 提交总数:45(不含 merge),涉及文件:182
### feat (6)
- [1ef9857] feat: API 测试技能新增契约转测试骨架生成脚本(Laffey-82)
```

**周报节选:**

```markdown
## 本周完成
- API 测试技能新增契约转测试骨架生成脚本,契约校验失败会直接拒绝(1ef9857)
- 任务拆解、技术文档技能新增检查脚本,产出可机器自查(45efbeb、651ea4b)
## 进行中
- 新技能周报生成,骨架已完成,正在补实测
## 风险与阻塞
- 无
## 下一步计划
- 跑完新技能实测后发 v0.8.0
```

## 辅助脚本

[scripts/collect_worklog.py](scripts/collect_worklog.py) 从 git 历史收集指定时间段的提交,按类型分组,统计文件数,琐碎提交单独列出:

```bash
# 本周一至今,当前目录仓库
python skills/weekly-report/scripts/collect_worklog.py

# 指定时间段 + 多仓库,输出到文件
python skills/weekly-report/scripts/collect_worklog.py --since 2026-08-24 --until 2026-08-30 --repos <路径1> <路径2> -o 草稿.md
```

脚本只做收集和分组,周报结论由人写。

## 注意事项

- **不编造**:脚本没收集到的、用户没确认的,不要写;
- **区分事实和结论**:提交是事实,"做了什么"是结论,结论由人确认;
- 给领导看的周报少写技术细节,给同组看的可以写实现细节;
- 多仓库汇总时,按仓库或项目分组,别混成一锅。

## 不适用场景

- 没有 git 历史也没有工作记录,要凭空写周报;
- 用户要的是日报(把时间范围调成一天即可);
- 纯个人流水账,不需要结构。

## 验证方式

1. 触发:"帮我写周报";
2. 跑脚本:collect_worklog.py 输出与 git log 抽查结果一致;
3. 走查:周报里每条"完成"都能对应到提交或用户确认过的事项;
4. 确认:用户过目后无异议。
